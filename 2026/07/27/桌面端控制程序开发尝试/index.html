桌面端控制程序开发尝试

前言

工作原因需要做一下地面站控制程序的开发，虽然感觉希望渺茫，但失败的尝试也是重要的经验积累过程，也能让我重新梳理一下现在比较新的开发框架。
现在的程序开发路径五花八门，新技术层出不穷，需要持续的学习，更新自己的知识。
最早接触C语言开发时，我还记得使用的是官方环境Visual C（也叫VC，MSVC），学习的时候我们喜欢用Dev C，在界面美观和错误诊断方面会更友好一点。
大型的C#开发，需要重型的开发环境Visual Studio，可视化的界面开发确实强大，但也是真的臃肿，牵一发而动全身，必须要做好周密的设计。
虽然现在有了AI辅助，一些简单的程序做起来已经比较容易，需要排半天BUG的代码，现在喝杯水的功夫就已经解决了。但是涉及到大型和多边协作的项目，依然需要许多的辅助和限制，已经多轮修改。
到真正碰到问题的时候，还得靠人的思考和判断，来分析和解决。大胆假设，小心求证，虚心学习，是通往成功的途径，成功是偶然，失败才是常态。

当前的痛点

当前无人机和水下机器人主要用的是QGC改的控制程序，QGC虽然强大，但也存在一些问题。

痛点 设计对策
1. GPL协议 没法闭源 不 fork QGC;协议内核用 Apache2.0 的 MAVSDK 或 MIT 的生成代码;UI 用 Qt 商业授权/WPF;视频库走动态链接。全链路无 GPL 传染。
2. 追不上 QGC 版本 自己的内核不跟 QGC 版本走,只跟 MAVLink 协议版本走(而 MAVLink 协议极稳定,常用消息十年没变)。协议升级只需重新生成消息定义,业务代码不动。
3. 功能臃肿、自检冗余、有些功能不适配 插件化 + 按需加载。用”载具抽象层”把无人机/船/潜航器做成三个插件,共用协议内核;自检、mission、参数校准这些都做成可插拔模块,涉密精简版直接不编译进去。

关于云端连接的问题：之前设计平台的时候，设计的是飞机可以直接联网，而水下机器人使用的是转发设计，只要地面站运行一个转发程序就行了，ROS2上运行的程序不变。这样做的好处是，不需要修改地面站程序。如果需要做自己的地面站程序，那也是先做好其他实际功能就可以，联网的功能什么时候都可以加入。

Mavlink

MAVLink 通信说穿了就是收发一堆结构化消息。做最小控制,你只需要处理下面这十几条消息(PX4/APM 的 common 消息集通用):

必须接收(下行遥测):

  • HEARTBEAT — 心跳,判断连接是否存活、飞控类型、当前飞行模式、是否解锁
  • SYS_STATUS — 电压/电流/电量
  • ATTITUDE — 姿态(横滚/俯仰/偏航)
  • GLOBAL_POSITION_INT / GPS_RAW_INT — 位置、高度、GPS 状态
  • STATUSTEXT — 飞控文字告警(自检失败原因都在这里)

必须发送(上行控制):

  • HEARTBEAT — 地面站也要每秒发一次,否则飞控可能进入失控保护
  • COMMAND_LONG — 万能指令:解锁/上锁- (MAV_CMD_COMPONENT_ARM_DISARM)、起飞、降落、返航
  • SET_MODE / COMMAND_LONG(DO_SET_MODE) — 切换飞行模式
  • MANUAL_CONTROL — 手柄摇杆控制(最适合船/潜航器,直接给 x/y/z/r 四轴量)
  • SET_POSITION_TARGET_LOCAL_NED — Guided/Offboard 模式下的位置/速度控制
  • PARAM_REQUEST_LIST / PARAM_SET — 参数读写(可以后期再做)

前端选择

QGC为了实现多端运行，使用的是Qt路线，并且版本还不同，一开始使用的是Qt5，后来升级到Qt6。Qt6有三种授权模式，可以开源，可以小团队闭源，商业版也可以完全闭源。但是这Qt for Android和Visual Studio 这两套开发环境相当沉重，而且，没有必要再做一个QGC。
所以这里我选择了用Electron框架+Web UI的方式，构建程序界面，

GCC

GNU Compiler Collection（GNU 编译器套件），实际上就是一个编译器，将文本的代码编译成可以被执行的文件。GCC的初衷是为GNU操作系统专门编写的一款编译器，这个系统早就凉了，被Linux内核取代，但后来扩展到linux、MacOC、Win，语言也从C扩展到C++、Fortran、Pascal、Objective -C、Java、Ada、Go等。
GCC是没有界面的，纯命令行，想要集成开发环境IDE，得自己去找。
使用示例。

MinGW-W64

MinGW，全称为 Minimalist GNU for Windows，是一个开发环境，旨在将 GNU 工具和库的强大功能带入 Windows 平台。它提供了一套轻便但功能齐全的工具，使开发者能够使用熟悉的类 Unix 开发流程编译并运行原生 Windows 应用程序。MinGW 在需要极简方法且不承担更复杂开发环境负担的程序员中尤其受欢迎。
因为一些原因MinGW已经不再维护了，而替代它的就是MinGW-W64。而还有一些类似的编译器LLVM-MinGW，是基于LLVM Clang的，不是GCC，也非常不错。去官网还能找到很多类似的东西。

Electron 框架

一句话概括就是跨平台框架，做前端界面的，并且专注于桌面应用，而不是Web服务器。
Electron是由OpenJS Foundation与开发者社区基于Atom Shell框架开发的跨平台桌面应用开发框架，该框架通过整合Chromium内核和Node.js运行时环境，允许开发者使用JavaScript、HTML及CSS构建兼容Windows、macOS与Linux系统的桌面应用，架构采用主进程处理系统级交互、渲染进程依托Chromium展示界面及IPC通信机制。
它相当于一个浏览器的外壳，可以把网页程序嵌入到壳里面，可以把网页打包成一个在桌面运行的程序，通俗来说就是软件。
大名鼎鼎的VS code 就是Electron做的，初次之外还有QQ、网易音乐等。

一个 Electron 应用有且只有一个主进程。并且创建窗口等所有系统事件都要在主进程中进行。
在正常的浏览器中，网页通常运行在沙盒封装化的环境中，并且不允许访问本机资源。然而，Electron 用户有权在网页中使用 Node.js 的 API，从而允许较低级别的操作系统交互。

Node.js

Javascript运行环境。浏览器的Javascript依赖浏览器环境，而Node.js可以让Javascript脱离浏览器，做后端服务。Javascript是车，Node.js是路，高速路是V8，赛车道是bun。

过程的问题

实际上用AI开发时，遇到了大量问题，地图时好时坏，Cesium死活加载不出来，加载出来尺寸又不对，改了几十轮。软件工程还真是没有那么简单，对于客观现实和自己的能力要有清晰的认知，虚心学习。

2D 地图瓦片:卫星与矢量图层覆盖冲突

2D地图始终无法正常显示，不是加载不出来，就是矢量图始终盖在影像图上面，就算要求去掉矢量图，只保留影像图，也做不到，仿佛一个幽灵调用始终存在，却查不到，非常诡异，按理说以AI的搜索能力，不应该出现这种小问题。

排查过程:
初始用 map.setStyle() 双样式切换——切换到卫星时旧矢量图层残留
改为 4 层 visibility toggle——竞态条件导致图层全部隐藏
改为 remove+add 源/图层——source ID 复用导致缓存串扰
删掉所有矢量代码,只保留卫星——仍有类似矢量的标注覆盖
确认为 style=9 标注层(sat-ann)的橙色道路+地名被误判为矢量——加上 curl 验证后其实卫星底图是正常的
最后还是没解决。

PS：后来我手动查代码，发现问题并不复杂，只要删除矢量图的加载代码就解决了，而AI不知道为何一直无法解决这个问题，太奇怪了。决定高德地图样式的是style参数，不同参数对应不同地图。

Cesium加载的问题

Electron框架做Cesium界面，也出现了一些不兼容的问题，按钮全部乱掉了，最后只能删掉处理，界面显示尺寸也不对，最后勉强改出来一个能看的版本。

  • Cesium 容器尺寸
    Cesium Viewer 初始化时容器尺寸不准确,导致 canvas 渲染在错误尺寸。

**解决:**通过 position: absolute; inset: 0; + JavaScript forceCesiumResize() 多次 resize 解决。

  • Cesium Widget 布局
    Cesium 自带 UI(widget 工具栏、sceneModePicker)布局异常,跑到窗口底部。

**解决:**隐藏所有 Cesium UI,计划用自定义控件替换。

阶段性成果

目前这一阶段，能把基础界面做好，显示出个大概来，就已经非常不容易。光是改地图显示和界面，就折腾了一下午。并且有相当多的情况，是反复修改之后依然报错，脱离了熟悉的开发框架，AI在查找问题的能力就骤然降低，仿佛一个刚学程序的萌新，根本找不到问题在哪。
为了解决地图显示的问题，甚至最关键的飞控连接都没时间做，也是够无奈的。

总结

以这次的实践结果看来，要想做好软件工程，吃透代码逻辑与底层架构，依然需要软件工程师的努力，否则有些疑难杂症根本无法解决。虽然使用的是DeepseekV4，但应该跟模型关系不是特别大，就算花了GPT、Gimini、KIMI K3之类的模型，也不保能解决，最后可能钱花了，还是一地鸡毛。
之前用AI搞python和HTML就非常容易，而一旦涉及到C、C++、就比较困难了。
