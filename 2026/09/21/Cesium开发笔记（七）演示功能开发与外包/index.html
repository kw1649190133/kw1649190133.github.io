Cesium开发笔记（七）演示功能开发与外包

前言

目前的平台虽然有一点演示功能，计划添加一点数据处理相关的功能。

纯演计划

  1. 补充数据，之前应该有多次飞行的数据。
  2. 飞机模型考虑做个优化。之前做过一个，但模型太大，细节太多，可以压缩简化，并且颜色材质丢失。
  3. 原始的数据大部分都是照片，没有直接的视频可用。可以根据重建后的影像，与无人机轨迹和画面投射的范围，反向生成实机画面的视频，这样做视频流的投影、实时扫描特效，就更加简单了。需要分析实现流程，用什么组件，大概需要单独做生成工具。使用不同的影像，航线一条就够，按照轨迹重新录制成视频。
  4. 提前绘制好管道矢量和影像对比结果，展示最终效果。也避免了ONNX识别的卡顿情况。利用精致的矢量来做热力图，效果应该不错。
  5. 两期影像对比，使用生成的视频在两个框里播放，顺便标记变化矢量，
  6. 制作循环播放开关。一键播放演示效果。
  7. 消息弹窗，报告实时的识别统计结果。

影像反向生成视频

实现路径

按照我的设想，从GADL和QGIS都可以实现，不过QGIS做的话，应该就没法打包成单独的工具了。

路线 技术 真实感 依赖 集成难度
A. GDAL + OpenCV 单应矩阵透视变换 平坦地面近似 轻，纯 Python，可打包 exe ⭐ 最易
B. QGIS Qgs3D 真实 3D 离屏渲染 高（有高程/阴影） 需完整 QGIS + PyQGIS ⭐⭐⭐ 难
C. Open3D / PyVista textured mesh 光栅化 高（有 DSM 遮挡） 中，纯 Python ⭐⭐ 中

几个必须提前想清楚的坑

  1. 坐标系：TIF 是投影坐标（UTM），轨迹是经纬度，必须用 pyproj 统一，否则整条航线会偏
  2. 倾斜视角缺侧面信息：DOM 是正射（垂直向下），大倾角时侧面拍不到真实内容，平坦地面假设会失真——所以第一版适合正射/小倾角航线，扫描特效完全够用
  3. 内参与分辨率绑定：fx = focalLength / pixelSize，你得先定”模拟相机”的画面分辨率（如 1920×1080），内参才能算对
  4. 帧率与轨迹密度：轨迹点间隔 vs 视频帧率不一致时要插值，否则画面一顿一顿
  5. ⚠对于海浪变化，在影像里是没法直观体现的，容易露馅。

执行步骤

  1. 确定航线。原始MRK转shp ? 包括点和线两种输出，表示原始的拍照点和航线，再把数据写进字段里。 或者不用MRK转换，重叠率太高，直接绘制shp，进行插帧，直接输入高度和投影范围，锁定参数；
  2. 插帧，增加点密度，确定拍摄位置，生成时间戳，至少按照30帧来进行设置，起始时间可以自己输入。飞行速度可以自己设置，比如放慢点按10m/s来，一般无人机好像是飞10-15m/s；(补充：其实应该在拐角处做圆滑处理，否则生成的画面截取框转弯会比较生硬)
  3. 计算投影图片，截取画面，拍摄中心点确定，自己指定投影到地面的长宽就可以了；（生成截取的矢量，再批量进行影像裁剪就可以实现了。需要注意可能会截取到影像范围外，以及当截取范围是有角度的，需要注意截取后修正角度，最后合成视频应该是正的。）
  4. 合成视频。（需要注意让视频的时间戳与航线的播放速度一致，这样才能保证后续预览的同步。）

遇到的坑

把所有画面全部截取完再进行合并，会占用非常多的存储空间，必须要分段处理，五百张一段，压缩成视频后体积会大幅减小，然后可以删掉帧图片。

程序实现

理论完成，实践可行，具体的代码不贴在这，可以单独写一篇文档。现在程序可以自己插帧，生成拍摄节点、航线、截取范围的矢量，然后自己完成画面截取、视频生成。
考虑到有需要一个矢量去裁剪多个影像的情况，做多期影像对比，需要在主程序中做分步控制的参数，把矢量生成、视频生成的步骤分开做。

前端改造

视频生成没问题之后，接下来就是前端的界面和功能了。

  1. 同一条航线对不同的影像，制作两期对比，同时在画面中播放。（或者是合成视频的时候直接给编辑到一起去，播放的时候给它留一个长一点的框就行，具体看同时播放是否方便实现。）
  2. 制作矢量标签，每个影像单独的标签、对比的标签。
  3. 画面与矢量的联动调试，矢量能够随着画面的显示而出现。
  4. 目前的设计都是基于二维影像的，后面可以考虑升级三维的方案，镜头画面可以有一定的倾斜角度。

遇到的问题

影像显示功能还需要调试和优化，目前影像属于图片直接加载，没有分级处理。一开始想尝试tif的加载，做瓦片分级处理，但后来发现并没有那么简单。jpg和png可以直接当成图片贴在场景中，但tif如果很大，需要做瓦皮切分、地图服务，光靠AI很难一键搞定。最后综合成本考虑，先选择tif转换压缩成png，一步加载的方案。重点是把总路线走通，这种细节只能等有机会再优化了。

设计

现在继续折腾设备连接功能，之前用AI做的连接程序虽然可以使用，但总是有各种各样的BUG，连接不稳定，时而出现时而消失，经常断联。数据库并非我擅长的领域，看来这部分得重新设计一下，初步的设想是将它独立出去，单独做一个组件，负责接收和推送实时数据，这样三维平台就只需要从服务器拉取数据就可以了。设想很美好，实现起来依然有点头大，涉及到许多的细节需要考虑。

前情提要

我需要做一个运行在服务器的云服务程序。
给无人船、水下机器人、无人机联网提供云服务。这些设备都是通过地面上的遥控器或者桌面端程序联网的，在遥控器输入账号和服务器地址，就可以连接到服务器。（需要显示连接情况，计算延迟等小功能）飞机和无人船也可以通过4g模块单独联网，上面有挂载linux系统，可开发的自由度还是比价高的。

关于实机连接的开发计划：

  1. 把实机连接的功能进行拆分（目前已经是分离的，本地的程序也可以连接云端服务器的设备管理），单独做云端设备信息的管理，需要重新梳理代码，拆分模块，还需要完善很多功能。
  2. 控制实时流量，避免数据通道阻塞， 优先保障设备基本状态的信息通畅。点云数据和相机画面还是有优化空间，用延迟换压缩率，提高网络带宽的利用效率。涉及到视频数据压缩、点云数据压缩的问题。
  3. 数据发送端的适配，先做独立程序，再考虑结合进控制软件，一键启动云端连接。其中的关键在于确定数据对接格式，解耦发送端与接收端
  4. 设备云端服务：
    用户管理、飞行管理、密钥管理、实时云播、历史回放、统计数据、任务推送、消息推送。
    设备直接联网或遥控器控制端联网后，发送位置和姿态信息。
    云端也可以给遥控器发送消息。
    标点和位置共享，
    用户管理设计，唯一超级管理员、管理员、用户、游客，这样应该比较合理。为了节约开发资源，先不考虑多层级组织与精细化权限体系。

云端需要暴露标准化api，前端组件化架构

设备接入协议：MQTT
消息总线与异步通信：采用 RabbitMQ 处理异步任务和事件；
实时数据推送：采用 WebSocket 全双工通信
视频流媒体服务：基于浏览器原生的 WebRTC 技术，实现多路高清视频的免插件、低延迟（毫秒级）回传与NAT穿透。

对象存储：采用 MinIO 或 S3，用于存储结构化日志、多媒体文件及离线回放数据

安全防护体系：构建双向防火墙、端到端加密（TLS/SSL）、细粒度权限（RBAC）与操作审计，保障无人系统免受恶意网络攻击

只能趁着开会去要资源了。

之前也考虑过大疆无人机的接入，官方提供两种方式，一种是使用大疆的SDK，开发自己的APP，然后就可以自定义通信协议；还有一种是通过大疆上云API，只需要使用大疆的Pilot 2作为网关，做相关的适配，然后接入设备管理，然后就可以和自研设备一样了。

外包设备连接层的开发

之前也尝试过设备连接部分的开发，但是效果一般般，这个方面纯靠AI编程恐怕有点难搞定。或许用前沿的超级大模型+xcode，也并非不能实现，自己做要思考的东西还是挺多的，而且也没把握在短时间内做好，尤其是一些数据库之类的，我也不是非常了解。

当前目标

单套服务端+ 浏览器管理界面（二维地图、视频播放、后台管理），最多支持 4 台设备同时在线、2路实时画面、1路激光雷达点云；对外提供查询 / 实时订阅 / 文件拉取接口

实现功能

  • 设备连接后，能够看到型号、时间、位置、姿态等数据（由推送端提供），用二维地图简单表示。当设备端开启画面推送后，可以看到实时画面。推送端会主动压缩画质、限制分辨率（720p 480p），确保流畅度。需要优先确保连接的稳定性、流程度、以及断联、重连、下线等机制。
  • 设备连接记录管理，可以保存历史数据，可查询、选择、删除。
  • 暴露接口，其他电脑或服务器可以拉取到实时的设备数据和画面，以便其他的开发。
  • 需要确定统一规范、可拓展的数据格式。（之前有尝试做过，可以参考）
  • 基础的用户登录和设备登录、密钥管理，不涉及组织。
  • 大疆的设备通过上云API后，也可获取到位置等数据和视频画面，拉取信息的接口与其他设备一致。

限制

本项目边界：只做云端的设备连接 + 基础数据 + 接口暴露 + 视频转发录制，以及基础的登录管理，不做复杂的数据应用和分析和设备端的程序；
设备端限制：设备端主动做传输压缩处理，视频只推压缩码流、点云只推抽稀帧、影像只推压缩代理图——原始数据一律不上传，避免挤占通道。

其他

当前服务器规格：2C 2G 4Mbps ，有两台。
考虑到可能性能不够用，追加到4C 8G 30Mbps 应该完全足够了。

需要成果

1、直接部署服务
2、源码和使用说明。

外包报价

1W级别

只有口头沟通，报价6000-7000，具体实施还需要聊细节。以最小化功能实现为主。

10W级别

报价8W，这个模块有拆分，有分阶段的实现设计，还提到需要与设备端进行联调。

总结

  1. 找外包的临时开发，价格大概在1W-10W，效果各有不同，可以通过完善细节和指标要求，获得更精确的价格。而真正的商业成熟软件，应该远不止这个数。
  2. 选择购买服务，也依然需要一定的沟通成本，多次的联调不可避免。
  3. 也不能完全外包，还是需要自己把握关键部分的程序。
